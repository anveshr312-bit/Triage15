# TRIAGE15 — AUTHENTICATION JUDGE Q&A DEFENSE

This document provides rigorous, architectural defenses to anticipated judge questions regarding Triage15's authentication architecture, cryptographic token verification, and data model.

---

### 1. Why Supabase Auth instead of Firebase?
- **Modern Standards:** Supabase Auth is built on GoTrue and provides native support for asymmetric ES256 (ECC P-256) JWTs out of the box, whereas Firebase uses proprietary token structures and libraries.
- **SQL / Relational Alignment:** Supabase's underlying architecture is relational and integrates cleanly with standard SQL identifier patterns (UUIDs), matching our PostgreSQL/SQLite relational schema without document-database impedance mismatch.
- **Open Standard Protocols:** Supabase issues standard OIDC/OAuth 2.0 compliant tokens verifiable by any standard JWT library (e.g., `PyJWT` with `cryptography`) without requiring vendor-locked SDK wrappers in the backend.

---

### 2. Why retain SQLite instead of migrating to Supabase PostgreSQL?
- **Speed & Hackathon Scope:** Migrating SQLite to remote PostgreSQL on deadline day introduces network latency, migration friction, and external availability risks.
- **Microsecond Latency:** SQLite running locally on NVMe or Docker persistent volumes provides microsecond read/write latencies for our Kuhn-Munkres bipartite matching algorithm and 15-minute authoritative timer ticks.
- **ACID Integrity & WAL Mode:** SQLite in WAL mode with foreign keys enabled satisfies 100% of the relational constraints, serializable transactions, and booking locks required by the platform.

---

### 3. What is a JWT?
A JSON Web Token (RFC 7519) is a compact, URL-safe container consisting of three base64url-encoded parts separated by periods:
1. **Header:** Contains token metadata (e.g., algorithm `ES256`, key ID `kid`).
2. **Payload:** Contains identity claims (`sub` user UUID, `iss` issuer, `aud` audience, `exp` expiration, `email`, `role`).
3. **Signature:** Cryptographic proof that the header and payload were generated by the legitimate private key holder and have not been altered in transit.

---

### 4. What is ES256?
ES256 stands for **ECDSA using P-256 and SHA-256**. It is an asymmetric digital signature algorithm based on elliptic curve cryptography (NIST P-256 curve).

---

### 5. How does asymmetric signature verification work?
In asymmetric signing:
- The **private key** is kept secret by Supabase Auth and used to generate the mathematical signature over SHA-256(Header + Payload).
- The **public key** is mathematically derived from the private key and published publicly via JWKS.
- Anyone in possession of the public key can verify that the signature could only have been produced by the corresponding private key. The verifier (FastAPI) never needs or sees the private signing key.

---

### 6. What is JWKS?
A JSON Web Key Set (RFC 7517) is an HTTP endpoint (`{SUPABASE_URL}/auth/v1/.well-known/jwks.json`) returning a set of public keys formatted as JSON objects. Each key has a key ID (`kid`), key type (`EC`), curve (`P-256`), and public curve coordinates (`x`, `y`). FastAPI uses `PyJWKClient` to fetch, cache, and rotate these public keys dynamically.

---

### 7. How does FastAPI authenticate requests?
1. The frontend attaches `Authorization: Bearer <access_token>` to API calls.
2. In `app.main`, the dependency `identity = Depends(get_current_student)` intercepts the request.
3. `auth.verifier.verify_token(token)` decodes the header, fetches the matching public key from the cached JWKS, checks that `"alg" == "ES256"`, validates the signature, and verifies that `iss`, `aud == "authenticated"`, and `exp` are valid.
4. FastAPI extracts `sub` (the user's UUID) and queries `auth_identity_mappings` in SQLite to resolve the authorized `Student` entity.

---

### 8. What is the difference between authentication and authorization?
- **Authentication (AuthN):** Proving *who you are*. In Triage15, this is handled by Supabase verifying email/password and FastAPI validating the cryptographic ES256 JWT signature.
- **Authorization (AuthZ):** Proving *what you are allowed to do*. In Triage15, this is enforced by SQLite business logic in FastAPI: checking whether the authenticated student is the assigned mentor or requester of a doubt, verifying mentor skill assessment levels, ensuring bounty sufficiency, and validating session state transitions.

---

### 9. How do you prevent student impersonation?
- In deployed mode (`ENVIRONMENT=production`), client-supplied headers like `X-Demo-Student-ID` are **strictly ignored**.
- Student identity is derived exclusively from the cryptographically verified `sub` claim inside the signed JWT.
- A client cannot alter their `sub` claim without invalidating the cryptographic signature.
- The `auth_identity_mappings` table has unique constraints on both `supabase_user_id` and `student_id`, preventing unauthorized binding.

---

### 10. Where are passwords stored?
Passwords are **never stored in SQLite or touched by our FastAPI application**. They are handled and hashed exclusively by Supabase Auth using industry-standard hashing algorithms (bcrypt/argon2) with per-user cryptographic salts.

---

### 11. Why does the frontend receive the publishable key?
The Supabase publishable key (or anon key) is a public API identifier. It identifies the client project to Supabase's API gateway and only permits operations granted by Row-Level Security (RLS) or public Auth endpoints (such as `signInWithPassword` or `signUp`). It cannot bypass authentication or read private data.

---

### 12. Why must the secret key remain private?
The `SUPABASE_SECRET_KEY` (service role key) bypasses all Row-Level Security checks and grants root administrative access to the entire Supabase project, including user creation, deletion, and administrative password resets. It is used strictly in local backend administrative scripts (`provision_demo_accounts.py`) and is never included in frontend builds or client bundles.

---

### 13. How are Supabase identities mapped to SQLite students?
Through the `auth_identity_mappings` table:
- When a user signs in, FastAPI checks if `supabase_user_id == sub` exists.
- For seeded demonstration accounts, `provision_demo_accounts.py` maps the Supabase UUID to seeded profiles (e.g. `student-08` for Henry, `student-01` for Alice).
- For new user registrations, FastAPI transactionally creates a new clean `Student` profile with a 100-point starter balance and `mentoring = False`.

---

### 14. How do demo accounts work without real email inboxes?
The administrative provisioning script uses Supabase's Admin API endpoint (`POST /auth/v1/admin/users`) with parameter `"email_confirm": true`. This marks the synthetic email address as verified immediately at creation time, bypassing email dispatch while satisfying Supabase's email confirmation requirement.

---

### 15. What happens when an access token expires?
The Supabase JavaScript SDK automatically schedules token refresh in the background using the user's persistent `refresh_token` stored in `localStorage`. Before an access token expires, the client obtains a fresh access token from Supabase and updates the Bearer header seamlessly without interrupting active mentoring sessions.

---

### 16. What happens when Supabase is unavailable?
Because FastAPI validates tokens statelessly using **locally cached public keys (JWKS)**, existing active sessions and API calls continue to be verified and served even during a temporary Supabase Auth outage. Only new logins or token refreshes are paused until Supabase connectivity resumes.

---

### 17. What are the remaining security limitations?
- **Stateless Revocation Window:** An access token remains valid until its 1-hour expiration time unless an active token revocation blocklist is maintained.
- **Client Session Revocation:** Immediate logout relies on the client deleting the stored token and Supabase invalidating the refresh token.
- **Single Server Architecture:** The current implementation uses an in-memory coordinator and local SQLite file, designed for a single-worker container deployment.
